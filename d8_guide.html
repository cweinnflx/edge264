d8 WASM Inspection Guide

Using V8's d8 shell to inspect the machine code generated for edge264's WebAssembly decoder on ARM (jamba device, Rock5B / Cortex-A76).

d8 version: 13.2.152.45   Target: armhf (ARM32 NEON)   Test file: 718 frames, 480x270 H.264

Examples use ./d8_armhf (32-bit ARM) with --no-wasm-bounds-checks --no-wasm-stack-checks to disable WASM safety checks. These checks add ~7.5% overhead on ARM32 due to limited registers. On aarch64 the overhead is only ~2.7%, so the flags are less important there.

An aarch64 build (./d8_aarch64) is also available and can be used with the same commands (without the check-disabling flags). The aarch64 version produces AArch64 A64 instructions instead of ARM32 T32/A32, and runs ~20% faster due to wider registers and additional architectural features.

What is d8?

d8 is V8's standalone JavaScript shell. It runs JavaScript and WebAssembly outside of a browser or Node.js, providing direct access to V8's internals. Unlike Chrome DevTools, d8 can dump the actual machine code that V8 generates for both WASM and JS functions.

V8 compiles code through multiple tiers:

  • Liftoff — baseline compiler for WASM. Generates code fast but without optimization. Single-pass, register-allocating compiler.
  • TurboFan — optimizing compiler for both WASM and JS. Generates high-quality machine code with inlining, SIMD vectorization, and register allocation. Takes longer to compile.
  • Maglev — mid-tier JS compiler (between Ignition bytecode and TurboFan). Not used for WASM.

For WASM, Liftoff compiles functions on first call (lazy baseline). TurboFan recompiles hot functions in the background. For JS, functions start as Ignition bytecode, get promoted to Maglev, then TurboFan when they're hot enough.

Key insight: d8 runs the same V8 engine as NRDP on the jamba device. The machine code you see in d8 is exactly what NRDP generates when decoding video.

Setup

Building edge264.wasm with function names

For d8 profiling and code inspection to show function names (instead of bare indices like wasm-function[44]), the WASM binary must include the name section. This requires two flags:

  • CFLAGS="-g" — tells the compiler to emit debug names into the object file
  • LIBFLAGS="--profiling-funcs" — tells the emscripten linker to preserve the WASM name section in the final .wasm output
Both flags are required. Using -g alone is not enough — emscripten's linker strips the name section by default even when debug info is present. The --profiling-funcs flag keeps it. Neither flag changes the generated code or optimization level; -O3 is still applied. 
# Build with function names preserved (used by build_demo.sh)
emmake make OS=wasm VARIANTS= BUILDTEST=no CFLAGS="-g" LIBFLAGS="--profiling-funcs"

# Verify the name section exists
wasm-objdump -h edge264.wasm | grep name
#   Custom start=0x... end=0x... (size=0x00000b20) "name"

This adds ~3KB to the binary (182KB → 185KB) with zero runtime performance impact.

Files needed in the working directory

./d8_armhf             # d8 binary (ARM32 hard-float)

The d8 decode script: run_decode.js

This script loads the WASM module, instantiates it with stub imports (no browser APIs needed), loads a .264 file into WASM memory, and runs the full decode loop with benchmarking. It runs a warmup pass first (which includes Liftoff compilation and TurboFan recompilation), then multiple timed passes using the fully optimized TurboFan code.

# Basic usage (3 timed passes after warmup)
./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks run_decode.js -- netflixtest.264

# Specify number of timed passes
./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks run_decode.js -- netflixtest.264 5

Example 2: WASM SIMD128 → ARM NEON Codegen

The most interesting inspection: how V8 translates WASM's platform-independent SIMD128 instructions into ARM NEON machine code. The edge264_find_start_code function is a compact example that uses SIMD to scan for H.264 start codes (00 00 01) in the byte stream.

Command

./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks \
  --print-wasm-code run_decode.js -- netflixtest.264 2>&1 | \
  grep -A500 'name: edge264_find_start_code' | \
  grep -A500 'compiler: TurboFan' | head -120

SIMD Instruction Mapping

WASM SIMD128ARM32 NEON GeneratedPurpose
v128.loadvld1.8 {d0, d1}, [r0]Load 16 bytes from memory
i8x16.eq (vs 0)vceq.i8 q3, q1, q2Compare each byte == 0
i8x16.eq (vs 1)vceq.i8 q2, q2, q4Compare each byte == 1
v128.bitselectvbsl q3, q0, q1Bitwise select (mask blend)
i8x16.shuffle (shift 14)vext.8 q4, q1, q3, #14Cross-register byte shuffle
i8x16.shuffle (shift 15)vext.8 q1, q1, q3, #15Cross-register byte shuffle
v128.andvand q0, q4, q0Bitwise AND of two masks
i8x16.swizzlevtbl.8 d0, {d2, d3}, d14Table lookup (byte permute, 8 bytes at a time)
u16x8.shrvshr.u16 q1, q2, #4Unsigned right shift per lane
v128.const (all 1s)vmov.i8 q0, 255Vector constant
ARM32 NEON uses q registers (128-bit, made of two d registers). The vtbl instruction only operates on 8 bytes at a time, so a 16-byte swizzle requires two vtbl.8 instructions. AArch64's tbl handles all 16 bytes in one instruction.

The inner loop (annotated)

This is the core of the start-code search. It processes 16 bytes at a time, looking for the 00 00 01 pattern:

; === Inner loop: scan 16 bytes per iteration (ARM32 NEON) ===

; Compare each byte against 0 (find zero bytes)
vceq.i8 q1, q2, q1           ; q1[i] = (data[i] == 0) ? 0xFF : 0x00

; Shift the previous zero-mask and current zero-mask to check
; for consecutive zeros across the 16-byte boundary
vext.8 q4, q1, q3, #14       ; shift right 14: prev[14..15] + cur[0..13]
vext.8 q1, q1, q3, #15       ; shift right 15: prev[15] + cur[0..14]

; AND the two shifted masks: true where TWO consecutive zeros exist
vand q1, q4, q1              ; two_zeros_mask

; Compare against 1 (find the 0x01 byte after the two zeros)
vceq.i8 q2, q2, q4           ; q2[i] = (data[i] == 1) ? 0xFF : 0x00

; Bitselect: result = two_zeros & is_one (true where 00 00 01 found)
vbsl q2, q1, q0              ; q2 = (q2 & q1) | (~q2 & zeros)

; Pack result to find the byte position of the match
vshr.u16 q1, q2, #4          ; shift to pack match bits
vtbl.8 d14, {d2, d3}, d14    ; permute low 8 bytes
vtbl.8 d15, {d2, d3}, d15    ; permute high 8 bytes
vmov q1, q7                   ; extract to scalar registers
cmp r0, #0                    ; no match? advance 16 bytes

; Match found: use clz to find exact byte offset
blx r4                        ; call wasm::word32_ctz
The mapping is nearly 1:1 — most WASM SIMD128 instructions compile to a single NEON instruction. The main exception is i8x16.swizzle which requires two vtbl.8 instructions on ARM32 (since vtbl only handles 8 bytes). On AArch64, this is a single tbl v0.16b instruction.

Example 3: JS Hot Loop Optimization

Inspect the machine code TurboFan generates for a JavaScript function that calls WASM. This shows the JS-to-WASM call overhead and how TurboFan optimizes the decode loop.

Script: js_hotloop.js

Wraps the decode loop in a named JS function and runs it multiple times to trigger optimization:

View full source 
// ... same WASM setup as run_decode.js ...

const ENOBUFS = 42;
const ENOTSUP = 138;

// The hot decode loop we want TurboFan to optimize
function decodeAllFrames(bufPtr, bufEnd, frmPtr, decPtr) {
  let u8 = new Uint8Array(mem.buffer);
  let nalPos = bufPtr + 3 + (u8[bufPtr + 2] === 0 ? 1 : 0);
  let frameCount = 0;

  while (nalPos < bufEnd) {
    const nalEnd = find_start_code(nalPos, bufEnd, 0);
    const ret = decode_NAL(decPtr, nalPos, nalEnd, 0, 0);

    while (get_frame(decPtr, frmPtr, 0) === 0) {
      frameCount++;
    }

    if (ret !== ENOBUFS) nalPos = nalEnd + 3;
    if (ret !== 0 && ret !== ENOBUFS && ret !== ENOTSUP) break;
  }

  flush(decPtr);
  while (get_frame(decPtr, frmPtr, 0) === 0) frameCount++;
  return frameCount;
}

// Run 3x to trigger TurboFan optimization (Ignition → Maglev → TurboFan)
for (let i = 0; i < 3; i++) {
  flush(decPtr);
  const count = decodeAllFrames(bufPtr, bufEnd, frmPtr, decPtr);
  print("pass " + i + ": " + count + " frames");
}

Command

./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks \
  --print-opt-code --print-opt-code-filter="decodeAllFrames" js_hotloop.js -- netflixtest.264

Output

What to observe

  • Deoptimization guards at function entry (tbz checking feedback vector bits)
  • Uint8Array type checks — TurboFan verifies the map/type of the typed array on each access
  • SMI (Small Integer) arithmetic — pointer values are tagged with shift-left-1; you'll see asr w8, w6, #1 to untag
  • WASM call sequences — calls into WASM go through JSToWasmWrapperAsm builtins
  • Overflow checks — adds + b.vs patterns guard integer additions against overflow

Example 5: Benchmarking Decode Performance

run_decode.js includes built-in benchmarking with performance.now(). It measures pure decode throughput — no rendering, no JS framework overhead — giving a clean baseline for optimization work.

Command

./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks \
  run_decode.js -- netflixtest.264                # 3 timed passes (default)
./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks \
  run_decode.js -- netflixtest.264 10             # 10 timed passes
./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks \
  run_decode.js -- other_video.264 5              # different file, 5 passes

How it works

  • Pass 0 (warmup) — decodes the entire file once, untimed. This triggers Liftoff baseline compilation and TurboFan background recompilation of hot functions.
  • Passes 1–N (timed) — each pass decodes the entire file again with performance.now() bracketing. All code runs as fully optimized TurboFan.
  • Summary — reports avg/min/max time, fps, and ms/frame across all timed passes.

  718 frames (Liftoff + TurboFan compilation)

Why d8 is valid for benchmarking: d8 runs the same V8 engine and TurboFan compiler as NRDP on the device. The WASM machine code is identical. There is no GC pressure (0% GC in profiling), no browser rendering overhead, and no JS framework in the measurement loop. The sub-0.5% variance across passes confirms stable, reproducible measurements.

Use --prof alongside benchmarking to identify which functions to optimize:

Version Comparison

Comparing the current HEAD against an older, known-faster version (f8809f7 — "General cleanup on and around Intra") on armhf with --no-wasm-bounds-checks --no-wasm-stack-checks.

How to compare

# Build the old version's WASM (uses SSE-to-WASM SIMD path)
emcc edge264.c -c -D__i386__ -D__x86_64__ \
  -msimd128 -msse -msse2 -msse3 -mssse3 -msse4.1 -msse4.2 -mavx -mavx2 \
  -std=gnu11 -O3 -flax-vector-conversions -Wno-override-init \
  -Wno-initializer-overrides -g -o edge264.o
emcc edge264.o \
  -sEXPORTED_FUNCTIONS=_malloc,_free,_edge264_find_start_code,_edge264_alloc,\
_edge264_flush,_edge264_free,_edge264_decode_NAL,_edge264_get_frame,_edge264_return_frame \
  -sSTRICT=1 -sALLOW_MEMORY_GROWTH=1 --profiling-funcs -o edge264.js

# Copy to device and benchmark
./d8_armhf --no-wasm-bounds-checks --no-wasm-stack-checks \
  run_decode.js -- netflixtest.264 5
The old version predates native WASM SIMD support in the codebase, so it must be compiled using the SSE compatibility path (-D__i386__ -D__x86_64__ with -msse through -mavx2). Emscripten translates these x86 intrinsics to WASM SIMD128 instructions. The current version uses native WASM SIMD directly.
The old version uses a 7-parameter edge264_decode_NAL API (with non_blocking and next_NAL output pointer). The run_decode.js script auto-detects this by checking decode_NAL.length and adjusts the decode loop accordingly.
